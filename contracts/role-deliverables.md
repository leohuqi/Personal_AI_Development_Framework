# 角色主成果与收件标准

这些是内容判断标准，不是九张必填表或新的批准流程。已有文档可按章节复用；简单任务只处理受影响内容。统一执行[补输入、研究与产出](../workflow/role-work-method.md)及按需[共用协议](../workflow/agent-protocol.md)。

| 角色 | 主成果 | 收件时检查 |
| --- | --- | --- |
| Master | 问题/目标、事实和缺口、工作顺序与角色、整合方案、取舍建议及 Owner 待决事项；milestone/iteration与进度、两阶段Handoff；一个阶段阅读入口 | 是否推进整体目标，识别内容不足和跨角色矛盾；Owner 能否清楚判断；不能只提交路由/执行流水 |
| Product Analyst | 产品定义、用户/场景、研究结论、核心旅程、High Level Specs与Feature Catalog、产品优先级/切片建议和业务验收 | 是否解决真实任务，行为是否明确，能否作为 SA/UI/模块设计输入；Catalog不能代替高层产品意图；实施级详细规格由Module细化 |
| Solution Architect | 技术初评、Catalog五级实现复杂度及理由/风险，连贯系统主方案，职责依赖、公共接口与数据归属、端到端正常/失败流程、技术比较、部署安全可靠性和演进 | 能否解释整个系统如何工作，方案具体、一致、可实现；目录、图与 ADR 支持正文而非替代正文 |
| UI/UX Designer | 任务研究、信息架构/流程、差异概念及取舍、Owner反馈后的Figma设计/确认，再按批准前端栈和原型授权制作高保真交互，及状态/响应式/UI Profile | 任务完成、信息理解、操作负担与项目特点；页面、tokens、热点数量和可点击本身不代表可用 |
| Module Architect | 依据PA/SA/已确认UI细化实施级Feature Specs，内部职责/结构、接口与数据结构、算法、事务/并发、物理存储/迁移、异常及测试设计 | 能否据此实施并遵循系统基线；不等待PA提供实施设计；具体化意图，新的产品取舍回PA/Owner |
| Feature Coder | 可运行实现、针对风险的测试、必要文档、可审查 PR、已知限制 | 是否完成已定义行为，复杂度合理且可维护，测试覆盖真实风险 |
| QA Tester | Test Cases（前置/步骤/预期/AC/TC-ID）、Test Results（实际/状态/环境/版本/证据）、核心任务/关键异常、可复现缺陷、回归范围、未测项 | 证据与环境能否支持结论；不把截图、mock 或设计审查当集成测试 |
| Independent Reviewer | 精确范围/版本、独立发现与影响、证据和明确结论 | 需求覆盖、整体方案、跨角色一致性、用户体验、可维护性与不必要复杂度；发现“字段合规但不好用/不完整” |
| Context Coordinator | 最小来源及版本、关键决定、开放问题、执行 ID 和交接引用 | 接收方能否继续；默认作为共享能力，只有跨会话/复杂冲突确有必要时分派独立角色，不堆叠文档 |

## Master 的收件与整合责任

先核对主内容：产品行为是否明确；系统方案能否支撑旅程；UI 是否匹配输入输出/权限/异常；模块设计是否遵循系统和产品；实现与验收是否一致。对未解决矛盾给出原始来源、具体缺口、负责角色及受影响下游，要求有边界返工；无需为未变部分重走全流程。

整合建议应区分事实、推荐、取舍、假设、Owner 待决事项与暂缓项。一个方案不能同时承诺互相冲突的数据归属、交互或成本。Master 可判断交付不足，不冒充独立专业审查，不自行接受 P2 风险或批准重大产品/UX/架构决定。

机器检查只能发现缺字段、错引用、依赖/授权不符，不能判定实际用户价值或系统方案充分。形式门禁、专业审查和 Owner 评价分别进行，参见[质量评价](skill-delivery-evaluation.md)。
