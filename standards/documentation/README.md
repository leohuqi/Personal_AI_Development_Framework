# 项目文档与交付追溯

为读者提供一个清楚入口，让需求、设计、实现、测试与批准可定位并随交付维护。日常默认 Lite：只更新当前变更涉及的内容。README 和少量 Markdown 即可采用本方法；不强制门户服务、目录、生成器、任务系统或新增审批。

## 权威来源与阅读入口

| 信息 | 权威来源 |
| --- | --- |
| 需求、设计、接口 | 项目已有版本化规范或规范系统 |
| 实现 | 对应代码仓库与准确提交/构建 |
| 工作、计划、依赖 | 项目选择的工作管理系统或既有任务记录 |
| 测试 | 原 Test Case、Test Run、CI 与报告 |
| 决定、批准、验收 | 实际授权人对明确对象/范围/版本的证据 |

同一内容只维护一份正文。文档入口、Feature View、RTM 都是导航或派生阅读视图，不成为第二份需求或结果数据库。已有工具优先复用；未使用任务系统的项目可以直接引用现有 Issue、PR 或明确任务，不要求接入某一产品。

## 按读者的问题组织

先展示概览和结论，再按用途列短链接，正文和版本/审计信息按需展开。每组先写一句“这里能回答什么问题”。以下是逻辑分类，按实际需要合并或省略，不要求创建同名目录或搬迁旧文件：

| 逻辑分类 | 回答的问题 |
| --- | --- |
| 概览与计划 | 要解决什么问题，近期交付什么？ |
| 产品与需求 | 用户任务、规则及验收条件是什么？ |
| 架构与设计 | 系统如何工作，模块、接口和技术取舍是什么？ |
| 功能与追溯 | 某功能有哪些设计、实现与验证依据？ |
| 工程与质量 | 如何验证，实际结果和缺口是什么？ |
| 运维（适用时） | 如何运行、部署、监测和恢复？ |
| 审阅与决定 | 现在请谁决定什么？ |
| 历史与参考 | 当时发生了什么，哪些已被替代？ |

架构分类内按系统概览、视图、模块、接口/数据、ADR 区分用途，不能混成无说明的长路径列表。长路径、准确修订和生成元数据作为次要信息；窄屏仍能阅读。真实布局、键盘和响应式需要实际浏览器验证，源码或文件阅读不能代替。

## Catalog 与最小关联

已有 Feature Catalog 就从它枚举全部正式功能，名称、阶段和稳定 ID 回到原 Catalog 维护；新增行应自然进入现有导航或派生视图。手工 Markdown 项目在同次交付更新原 Catalog 的链接，不复制一张需同步的功能总表。未来功能可查找并显示缺少设计/实现/测试，不能补造证据或强制逐功能建规格。

已有规模化入口按 Feature ID/名称、阶段和来源状态定位，沿链接查 Requirements/AC、Design、Implementation、TC/Run；小项目可使用 Markdown/编辑器搜索。没有阶段或外部状态时注明不适用，不发明字段。

关联沿用[RTM约定](../../contracts/requirements-traceability.md)，只补稳定 ID、关系类型、权威引用、来源修订和必要核验状态。支持多对多、正向查证和从结果反查需求；不复制需求正文、测试步骤和结果。不规定项目必须采用 JSON、固定状态枚举或某套目录。

工作进度、设计批准、测试已设计、自动化已实施、执行结果、完整 AC 验证、Owner 验收分别显示其原结论。部分测试 PASS 不代表完整 AC；合并不代表验收。完整 AC 结论来自原 QA 报告，入口不再计算一套业务验收算法；无充分证据就显示未验证/证据不足。

## 每次交付只维护受影响内容

PA 维护需求/Catalog；SA/MA 维护设计/技术契约与有效版本；Coder 检查代码变化对应的需求、设计、接口、使用说明和测试引用，无影响时简述理由；QA 维护 TC/Run/缺陷和实际被测版本；Master 协调导航、必要关系与受影响外部状态；Reviewer 检查这些信息是否一致、过期或重复。

在已有任务/PR中说明文档影响、实际更新和未完成项，沿用[交付报告](../../contracts/delivery-report.md)。不新增 Documentation Manager，不要求每个 PR 全库审查、完整新报告或重新批准未变资料。机器可整体重建派生内容，人工审查仍只覆盖影响范围。

## 来源版本与过期检查

分开记录三件事：来源修订（Git commit/文档版本）、来源观察时间、入口生成时间。每条动态状态带来源及观察时间；只刷新一个条目不能刷新其他条目或暗示全库同步。读取失败时保留上次观测并标明失败/陈旧/未知，不能用生成时间冒充核验时间。

Git源先提交正文，再取得实际修订，为受影响路径更新版本引用，生成并提交派生视图。固定引用的内容应能从该修订真实读取并与展示一致；哈希可辅助比对，不能代替可解析版本。历史批准仍绑定原批准对象与旧版本，不跟随新正文迁移。外部规范使用可核验版本/快照及访问限制，不伪造 Git SHA。

使用生成页的项目复用本项目工具/CI，按风险检查：

- **先检查已提交派生结果是否过期，再重建。** 生成器/模板/数据变化也应使相关输出接受检查；在隔离目录重建比较，不能覆盖工作区后再宣称原提交有效。
- 检查关键路径、锚点、稳定 ID、关系端点和孤儿引用；未完成的未来对象标缺口，不能用伪关系消除警告。
- 检查实际展示的所有输入，包括正文及测试/状态数据，是否与固定来源版本一致；历史引用不能悄悄打开当前同路径内容。
- 记录必要的历史对象是否可访问；缺权限、缺 Git 历史或 Artifact 到期时如实说明，不静默回退到当前 HEAD。

静态 Markdown 入口不需要新增构建步骤，只核对受影响链接、版本和语义。没有生成物就没有“派生页过期”检查。框架示例的机械检查不是接入项目已完成这些验证的证据。

## 当前审阅入口

先列当前问题、推荐、影响/重大风险、准确交付版本、QA/Reviewer结论、未测/待决项，最后链接原证据。Owner可在原入口或对话反馈，由Master记录适用范围/版本；入口不授予批准权。

旧文中的待审字样不能直接进入当前待决清单。先核对后续批准、关闭、替代和适用范围；部分批准不能抹掉其余开放事项。无待决事项时写清楚空状态，不生成空报告。Dispatch、Handoff和原始执行日志按需阅读，不置于主成果之前。

## 裁剪、工具与接入

| 深度 | 适用范围 | 最小成果 |
| --- | --- | --- |
| Lite（默认） | 一个功能、PR或局部设计 | 更新受影响正文/引用/导航并做必要核验，可直接在原README/PR完成 |
| Standard | 一个阶段或相关功能组 | 归并相关入口、双向追溯与质量/待决信息，不审无关内容 |
| Full | 首次建立入口或获授权全项目复核 | 检查全部正式Catalog和主要分类、当前/历史及来源版本，不补写未来全部规格或TC |

按项目已批准 PADF tag/commit 采用；已有项目从当前切片增量接入，不搬迁目录、不补造历史、不因缺新字段自动失败。尚无 Catalog 的小任务直接引用需求/AC；达到多功能规模时复用原计划建立索引。可使用 Markdown、静态 HTML 或现有文档工具，由负责人依成本、私有访问、本地浏览和维护能力选择。现有工具不被迫迁移，不默认公开部署，不建立常驻同步或独立文档数据库。

普通资料维护由Master按需调用[共享Skill](../../.agents/skills/project-documentation-curator/SKILL.md)，不成为每个角色启动的前置阶段。最小入口写法见[可选模板](../../templates/documentation-entry.md)，合成演练见[验证入口](../../tests/documentation/README.md)。既有工程、架构、术语、Design Gate、G-01与授权要求不变。
