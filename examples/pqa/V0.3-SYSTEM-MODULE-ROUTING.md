# V0.3 system/module design routing example — PQA (illustrative)

This is **an example only**, not instructions to change PQA, its technology baseline, existing Feature statuses or Draft PR #7.

1. **New PQA platform or replacing data platform/architecture:** Master selects `architecture_scope: system` and routes `solution-architect`. It establishes an approved system tech stack, application/module boundary map and ADR, with architecture/technology diagrams. This is a separate architectural design task; do not infer an existing approval.
2. **Existing PQA strategy-analysis API enhancement inside an approved baseline:** Master selects `architecture_scope: module`. It reads the real current system architecture and its approved SHA and routes **only** `module-architect` to design package, service interface, code-level module diagram and test seams. Do not invoke Solution Architect for every normal feature.
3. **New application plus first expense-import module:** Master first establishes `architecture_scope: system` to design application baseline. In a second authorized stage, `architecture_scope: module` designs the importer and expense domain modules. Or choose `architecture_scope: both` with explicit `SYSTEM -> MODULE` dependency and immutable baseline handoff; not concurrent.
4. **UI-only appearance adjustment:** Master uses UI Designer and `architecture_scope: none`; no architect unless impacts require it.
5. L/XL, or risk-triggered S/M, requires independent DESIGN review of whichever packages are actually required; Master manages Gate, Owner approves material design changes and separately authorizes Coding.

A changed approved system baseline makes dependent module design `STALE` until reassessed. No actual PQA Linear/GitHub writes or implementation are authorized here.
