# 共用工作方法：补输入 → 研究 → 产出

所有角色开始前先读目标项目 AGENTS.md、获授权任务与相关现有材料，按当前角色和变化范围加载；同一规则不再复制到每个 Skill。没有变化的批准研究、规格和设计按精确版本复用。

## 不过度设计：最小充分，而非模板齐全

所有角色先复用，再只补当前验收或真实风险需要的内容。新增功能、服务、依赖、抽象、角色或文档时，说明对应的当前需求/约束，以及更简单做法为何不够；依据不足就删除或暂缓，并写重新评估条件，不预建未来能力。

当前行为足以实施/验证、关键边界和必要决定已清楚时停止细化。研究证据足够支持本次建议后停止搜索；常规细节交负责角色按批准基线处理，不把决定甩给 Owner。完整性是没有关键缺口，不是穷尽未来功能、章节、图表、状态或技术清单。

简单任务可同文合并规格和交接、复用角色；复杂/高风险任务仍补必要失败路径、接口、独立审查与授权。未知必须显式说明，不能为了简短藏掉关键风险、把未测写 PASS 或跳过已触发门禁。

## 文档、评审与沟通同样最小充分

这条原则适用于所有角色及接入项目的规格、设计、代码说明、测试报告、评审、PR、交接和日常状态更新，不只约束最终交付物。

- **结论或请求先行。** 第一段说明结果/推荐，或请谁决定什么；随后只补判断所需的理由、影响、重大风险与下一步。背景、过程和机器证据按需链接，不按执行时间线铺陈。
- **同一内容维护一份。** 优先更新原文及可引用章节；其他位置只给最小摘要和直达链接，不重复规格、发现、用例、日志或批准正文。链接注明用途，涉及批准/审查/交接时固定准确版本；读者仍需看懂当前结论，不能只甩链接。来源不可访问时说明缺口，并在权限范围内补必要内容。
- **只写本次变化。** 增量任务列变化、影响与未决项，未变内容引用有效来源；不为模板齐全新建报告或重复台账。普通进度只更新原入口，实质决定、版本变化和责任交接才追加必要记录；不可变历史证据保留原样。
- **评审聚焦实际问题。** 先给唯一结论、阻断/需决定事项及建议，再列按影响排序的发现；无发现就简短说明范围、准确版本和验证局限。检查受影响内容，复审核对新差异及受影响风险；不因个人格式偏好要求扩写或重做无关检查，旧版本批准仍不能自动覆盖新版本。

清晰、足以判断和继续工作即停止扩写。链接复用不省略必需协议字段、真实执行、独立性、重大风险或授权；已有事实和证据可精确引用，缺失不能补造。下列短卡片是阅读辅助，不强制每条消息填写全部项目。

## 架构与术语按需使用

依[架构方法](../standards/architecture/README.md)把总体导航、系统、模块和实施契约分层；按当前问题读取精确权威来源，已迁规则单份维护，尚未迁移的完整规则保持明确引用。角色不必读全包，Profile不豁免既有强制门禁。

依[术语规范](../standards/terminology/README.md)优先通行、自然且准确的表达，只加载相关领域词条；必要时使用[共享术语Skill](../.agents/skills/terminology-governance/SKILL.md)。项目定义由项目维护，不能为了文字一致而重命名技术标识、改变权限/行为/批准状态；不为普通文档改动新建审批。

## 给人看的建议与评审

所有角色需要人介入时使用[短卡片](../templates/stage-delivery.md)：请谁判断什么、我的推荐和理由、实际影响/风险、怎样回复、对应成果及版本。先说明用户/交付影响，再按需要解释术语；通常一屏可读，复杂内容先摘要，重要风险在主文。

技术判断交技术负责人，产品方向/重大取舍和授权交 Owner。只提供有实质差异的备选，不为凑选项扩写；已有有效批准直接引用。详细设计、机器字段与执行审计放链接/附录，由 Agent 核验，不要求人填 schema。收到/技术确认/方向反馈不能被解释成另一种动作的批准。

## 判断输入是否支持当前决策

| 情况 | 下一步 |
| --- | --- |
| 目标、用户、核心任务、重要约束或成功标准不清楚 | 先查已有材料；仍有缺口时集中问 Owner，说明缺什么、影响什么、建议选项及推荐。关键答案未到前暂停依赖它的设计，可继续不依赖该答案的授权研究。 |
| 目标清楚，产品/技术方案未定 | 主动研究真实可选方案，结合任务、成本、安全和现有基线提出建议。常规技术取舍不直接甩给 Owner。重大决定仍由 Owner 批准。 |
| 已有有效规格，且本次范围未变 | 复用来源和决定，只核对受影响内容；无需再次采访、竞品扫描或重新设计。 |
| 只有局部变化 | 明确差异、受影响旅程/契约/风险和需更新的批准；不重做无关设计。 |

问题关注方向：核心任务、使用习惯、体验偏好、数据安全、成本与成功标准。一次集中提出相互相关的少量问题，已有答案不得重复询问。依赖关系不清不能用“默认同意”推进；研究、提案、自检、审查与 Owner 批准分别标识。

## 用问题控制研究

把研究放在已有产品/技术文档的一个可引用章节中，或复用同一份研究记录，不为每个角色再复制一份。

- 写明要支持的决策、相关用户任务、约束、已有证据和停止条件；范围足以支持建议后停止，不做无目标的信息收集。
- 选少量有代表性的产品或技术选项，比较如何完成同一真实任务：步骤、输入输出、反馈、撤销/拒绝、错误恢复、成本和限制。功能清单、截图数量或宣传资料不能替代任务比较。
- 将做法和 Best Practice 放回项目约束中，解释适用、需调整、不采用的原因；给出推荐与替代方案，而不只罗列材料。
- 每个影响结论的证据区分 OFFICIAL_SOURCE（官方资料）、AGENT_EXPERIENCE（实际操作及环境/步骤/结果）、USER_RESEARCH（真实参与者与方法，保护隐私）、INFERENCE（Agent 推断）、ASSUMPTION（待验证假设）。标记来源及观察日期、局限和待验证项；资料阅读不能冒充产品实测或用户研究。
- 新角色先读取共享结论、适用范围与版本，只补变化或证据缺口；来源不可用时如实标记，不编造调研或测试。

最小研究记录可直接用一段正文加表：`决策问题 | 关键任务/选项 | 观察与来源/证据类别 | 对本项目的适用性 | 采用/调整/放弃及理由 | 未验证假设`。不是每项任务都必须新建该表。

## 交付与收件

先区分本次是框架方法评估、项目工程建设还是业务实施，见[适用范围](../standards/engineering/README.md#先分清本次任务)。规范升级从已有案例判断方法作用，不默认写配套工具或运行案例项目。资料检查/本轮亲自执行、方法机制可用/业务质量改善分别陈述；无法证明提效时列证据缺口，不靠新增演示测试补成结论。跨项目输入遵循[上下文加载边界](../governance/context-loading.md)。

软件实施按[共享工程标准](../standards/engineering/README.md)渐进建立测试策略、当前Functional场景/TC、适用TDD/调试/完成核验和可追溯报告。复用既有架构/ID/CI与成熟工具，不另开全套工程流程；工程深度按风险独立裁剪，不豁免原授权/安全/Review。实际结果固定三版本及环境，失败/跳过/阻塞/未测如实，Unit通过、AC验证、Owner验收不互推。用准确链接共享用例和结果，不为每个角色复制正文或每次微循环造报告。

先说明解决了什么问题、推荐方案、关键取舍和待决事项，随后链接主产物；执行/协议证据置于附录。同一文档可承载多个交付章节，Catalog 只做索引。

按[角色成果标准](../contracts/role-deliverables.md)检查具体性、覆盖及一致性。Master 对明显缺失、与产品行为冲突、无法支撑下游实施或复杂度不合理的内容返回 NEEDS_REFINEMENT，指明缺口及受影响任务；不以字段齐全、文件/页面/热点数量或图表存在判定有用。此收件判断不代替独立 Reviewer，也不批准重大决定或编码。

复杂度与风险决定角色和细节：简单缺陷可直接使用已有 Feature Spec 与基线；不为流程完整而启动全部角色。模块设计与编码不得临时猜测产品规则，问题回到 Product Analyst/Master。

## 参考依据及适用边界

[GOV.UK Discovery](https://www.gov.uk/service-manual/agile-delivery/how-the-discovery-phase-works)强调理解问题、用户和约束，并以成功标准判断后续投入；这里采用其判断方式，不照搬团队规模或周期。

[NN/g 竞品评估](https://www.nngroup.com/articles/competitive-usability-evaluations/)区分专家比较与真实用户测试，并围绕关键任务支持设计选择；本框架不把 Agent 资料分析称为用户研究。

[arc42 模块视图](https://docs.arc42.org/section-5/)与[运行视图](https://docs.arc42.org/section-6/)分别帮助解释职责依赖与代表性协作场景；[Google 审查实践](https://google.github.io/eng-practices/review/reviewer/looking-for.html)提供整体设计、功能适用性与不必要复杂度的审查依据。这些是参考实践，不是项目已完成实测的证据。

## 文档随交付维护

按[文档标准](../standards/documentation/README.md#每次交付只维护受影响内容)，每次交付主动检查文档影响、更新原来源和中心受影响条目，并按实际命令检查/生成/核验，不等Owner逐次提醒；无影响简述理由。交付给出可打开的中心入口与实际同步结果/未完成项，Master收件核对。默认Lite，不要求每次重建全库；缺中心按原接入任务补建，小任务可用README。生成式中心落实项目PR/主分支自动化，静态入口不造构建。共享整理Skill按需调用，不让每个角色预加载门户资料。
